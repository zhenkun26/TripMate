## ADR-TM-001：单次 PlannerAgent 双阶段规划 + 契约修复

- **背景**：产品需要同时满足整体路线排序、每日细化和稳定的结构化输出。
- **候选方案**：多次独立模型调用；单次调用但自由文本；单次调用输出结构化 `TripPlan`，失败后有限修复重试。
- **选择**：一次 PlannerAgent 调用完成“整体粗排 → 每日细化”，Pydantic 校验失败时最多修复 2 次；预算中的门票总额由后端重算。
- **放弃**：把金额和最终契约完全交给模型；无限重试。
- **验证**：OpenSpec design/tasks 记录契约校验和重试设计；README 记录后端测试与 CI 命令。具体运行结果以对应 CI/测试报告为准。
- **改判条件**：模型输出失败率、修复成本或路线质量证明需要拆成多个可独立评测的规划阶段。

## ADR-TM-002：Redis 只做优化层

- **背景**：天气、POI 和静态图需要缓存，但 Redis 不应成为行程生成的功能性单点。
- **候选方案**：缓存不可用即拒绝请求；所有状态改用 Redis；Redis 作为可绕过的优化层。
- **选择**：Redis 可用时共享缓存和限流计数；不可用时缓存绕过并直调外部服务，按 README 声明保持功能可用。
- **放弃**：把缓存命中作为业务正确性的前提。
- **验证**：README 记录缓存 TTL、重连和降级语义；需要持续用集成测试确认 Redis 断线后的行为。
- **改判条件**：外部 API 成本或配额要求缓存必须具备强一致/持久化能力。

## ADR-TM-003：后端代理静态地图，前端只接收不透明 token

- **背景**：地图 Key 不能下发浏览器，同时需要让分享图和行程结果复用静态地图。
- **候选方案**：前端直接调用高德；后端返回完整地图 URL；后端保存参数并通过不透明 token 代理图片。
- **选择**：后端把地图参数写入 Redis，返回 `/api/trip/static-map/{token}`；代理负责取参、调用高德、限流并同源返回 PNG，失败时返回空 URL 让前端隐藏地图。
- **放弃**：把 Key 或可篡改的地图参数暴露给前端。
- **验证**：OpenSpec design 明确了参数、token、限流和失败路径；需以实际 API/集成测试继续验证过期 token 和外部失败。
- **改判条件**：改用具备同源安全代理和签名 URL 的地图服务，或分享链路需要独立对象存储。

## ADR-TM-004：前端契约由后端模型生成

- **背景**：前后端计划、预算、天气和分享结构必须保持一致，手工维护类型容易漂移。
- **候选方案**：前端手工维护类型；运行时宽松解析；Pydantic → JSON Schema → TypeScript 自动生成并在 CI 检查 diff。
- **选择**：以后端 Pydantic 为事实源，生成 `contracts.generated.ts`，禁止手工修改；CI 重新生成并要求工作树无 diff。
- **放弃**：把契约漂移留到运行时发现。
- **验证**：README 已记录生成命令和 CI 门禁；契约变更必须同时检查后端测试与前端构建。
- **改判条件**：跨语言契约工具无法表达新类型，或服务拆分后需要独立版本化契约。
